# Frontend Integration Guide for `POST /chat/turn`

## Purpose

`POST /chat/turn` is the main conversational endpoint in this codebase. The backend does not keep chat session state on the server. Instead, the frontend is responsible for sending the latest conversation state on every turn and replacing that local state with the `next_context` returned by the API.

## Endpoint

- Method: `POST`
- Path: `/chat/turn`
- Content-Type: `application/json`

## Frontend Responsibilities

The frontend should own and persist these values for the active chat session:

- `session_id`
- `customer_id`
- `context`
- `transcript`

For each turn:

1. Send the current `context` and full `transcript`.
2. Render the backend response.
3. Replace local `context` with `response.next_context` when present.
4. Append the bot reply to `transcript`.
5. Continue until the backend returns a handover or your UI intentionally starts a new session.

## Request Contract

### Request shape

```json
{
  "session_id": "sess_abc123",
  "customer_id": "cust_001",
  "message": "My order is delayed",
  "message_type": "text",
  "option_id": null,
  "context": {
    "current_flow": null,
    "flow_step": null,
    "category": null,
    "order_id": null,
    "turn_count": 0,
    "negative_turns": 0,
    "fallback_count": 0,
    "open_handovers": []
  },
  "transcript": [
    {
      "role": "customer",
      "content": "My order is delayed"
    }
  ]
}
```

### Request fields

| Field | Type | Required | Notes |
|---|---|---:|---|
| `session_id` | string | Yes | Generated by frontend. Backend does not create it. |
| `customer_id` | string \| null | No | Important for order lookup and repeat complaint escalation. Send it every turn if available. |
| `message` | string | Yes | Human-readable content for the current turn. |
| `message_type` | string | Yes | In practice this codebase uses `text`, `option_select`, and `upload_complete`. |
| `option_id` | string \| null | No | Required when the user clicks a backend-provided option. |
| `context` | object | Yes | Current chat state from previous response, or empty state on first turn. |
| `transcript` | array | Yes | Full conversation transcript accumulated by frontend. |

### Initial empty context

```json
{
  "current_flow": null,
  "flow_step": null,
  "category": null,
  "order_id": null,
  "turn_count": 0,
  "negative_turns": 0,
  "fallback_count": 0,
  "open_handovers": []
}
```

## Supported Turn Types

### 1. Free text

Use when the user types a message.

```json
{
  "message": "I want to cancel my order",
  "message_type": "text",
  "option_id": null
}
```

Behavior:

- Triggers NLU classification.
- May update `context.category`.
- May update `context.order_id`.
- May increment `negative_turns`.
- May increment or reset `fallback_count`.
- May escalate immediately depending on intent, sentiment, or prior open handovers.

### 2. Option selection

Use when the backend returned `render_type: "options"` and the user clicked one of the options.

```json
{
  "message": "Yes, connect me to an agent",
  "message_type": "option_select",
  "option_id": "ok"
}
```

Behavior:

- Does not run NLU.
- Navigation is driven by `context.flow_step` plus `option_id`.
- `message` can be the selected option label for transcript readability.

### 3. Upload completion

Use after the frontend completes required media upload UX.

```json
{
  "message": "upload_complete",
  "message_type": "upload_complete",
  "option_id": "upload_complete"
}
```

Behavior:

- Does not run NLU.
- Advances the current flow via the `upload_complete` transition.
- The backend does not accept uploaded binary files in this endpoint. Upload handling is frontend-side or external to this API.

## Response Contract

### Response shape

```json
{
  "render_type": "options",
  "message": "I can help with payment & billing! Please select your query:",
  "options": [
    { "id": "refund", "label": "I want to know my refund status" }
  ],
  "upload_config": null,
  "terminal": false,
  "escalate": false,
  "escalate_reason": null,
  "ai_summary": null,
  "next_context": {
    "current_flow": "flow_payment",
    "flow_step": "flow_payment",
    "category": null,
    "order_id": null,
    "turn_count": 1,
    "negative_turns": 0,
    "fallback_count": 0,
    "open_handovers": []
  },
  "nlu": {
    "intent": "payment_query",
    "category": "unknown",
    "confidence": 0.97,
    "sentiment": "neutral",
    "order_id": null,
    "entities": [],
    "source": "keyword"
  },
  "ticket_raised": false,
  "issue_type": null
}
```

### Response fields

| Field | Type | Meaning |
|---|---|---|
| `render_type` | string | UI mode the frontend should render next. |
| `message` | string | Bot text to show in chat. |
| `options` | array \| null | Buttons/chips to render when `render_type` is `options`. |
| `upload_config` | object \| null | Upload requirements when `render_type` is `upload`. |
| `terminal` | boolean | End-of-flow signal. Not heavily used in current flow definitions, but supported by schema. |
| `escalate` | boolean | Whether the conversation should hand over to a human agent. |
| `escalate_reason` | string \| null | Machine-readable escalation reason. |
| `ai_summary` | string \| null | LLM-generated summary for handover. Present on escalation. |
| `next_context` | object \| null | The new state to store locally for the next API call. |
| `nlu` | object \| null | NLU result. Present only for text turns. |
| `ticket_raised` | boolean | Indicates the flow considers a support ticket raised. Useful for UI badges or analytics. |
| `issue_type` | string \| null | Issue classification emitted by some upload flows. |

## Render Types the Frontend Must Support

### `options`

Render:

- bot message
- clickable options from `response.options`

Frontend behavior:

- Disable free text input while waiting for a required option click.
- On click, call `/chat/turn` with `message_type: "option_select"` and `option_id` set to the clicked option ID.

### `upload`

Render:

- bot message
- upload instructions from `upload_config`

`upload_config` may contain:

- `required`
- `min_photos`
- `video`
- `max_size_mb`

Frontend behavior:

- Collect assets outside this endpoint.
- After the upload flow is complete, call `/chat/turn` with `message_type: "upload_complete"` and `option_id: "upload_complete"`.

### `handover`

Render:

- bot message
- escalation indicator
- `ai_summary`
- optional escalation reason for support/debug use

Frontend behavior:

- Treat the automated conversation as ended.
- Do not expect `next_context`; the backend returns `next_context: null` on handover.

### `text_input`

This appears in delivery-instructions flows.

Render:

- bot prompt
- normal text composer

Frontend behavior:

- Keep text input enabled.
- Next user message should be sent as `message_type: "text"`.
- The backend uses a wildcard transition for those steps, so any text will advance the flow.

### `text`

The schema allows it as a default fallback. Current flow definitions mostly return `options`, `upload`, `handover`, or `text_input`.

## State Management Rules

### `context` is the source of truth

The backend flow engine uses:

- `context.current_flow`
- `context.flow_step`
- `context.category`
- `context.order_id`
- `context.turn_count`
- `context.negative_turns`
- `context.fallback_count`
- `context.open_handovers`

Practical rule:

- Always overwrite local context with `response.next_context` when it exists.
- Never try to infer the next flow client-side.

### `transcript` is frontend-maintained

The backend uses `transcript` mainly for AI summary generation during escalation.

Recommended transcript pattern:

1. Append the customer turn before calling `/chat/turn`.
2. After the response arrives, append the bot message.

Message format:

```json
{ "role": "customer", "content": "I want to cancel my order" }
```

```json
{ "role": "bot", "content": "I can help with your cancellation. What type of order is it?" }
```

## Escalation Behavior

The frontend should be ready for escalation on any turn.

Current escalation triggers include:

- user explicitly requests an agent
- fallback count reaches 3
- repeat complaint on same `order_id` and `issue_type` with an open handover
- payment query
- electronics issues for quality/missing/wrong item flows
- 2 or more negative-sentiment text turns
- explicit `ESCALATE` step inside the flow graph

When escalation happens, response behavior is:

- `render_type = "handover"`
- `escalate = true`
- `next_context = null`
- `ai_summary` is returned

## Order Selection Behavior

Some steps ask the backend to fetch recent orders before returning options.

These are the `flow_order_select_*` steps in [engine/flows.py](/home/ashish/Documents/GitHub/Reatailgpt-mvp/engine/flows.py).

### Frontend implications

- The frontend does not call the orders API directly through this chat contract.
- The frontend only calls `/chat/turn`.
- If the backend can fetch orders, it returns them as normal `options`.

### Important category limitation

The internal order lookup adapter only supports:

- `fb`
- `fashion`
- `electronics`

It does not support `grocery` in [engine/order_lookup.py](/home/ashish/Documents/GitHub/Reatailgpt-mvp/engine/order_lookup.py).

Result:

- grocery order-select steps auto-skip when no supported order lookup is possible
- the backend prepends a notice like "We couldn't find any recent orders for your account."
- the frontend should simply render the response it receives and should not assume an order picker will always appear

### Order ID capture

When order options are returned from backend order lookup:

- selecting an option sends its `id` as `option_id`
- backend may store it into `context.order_id`

This is handled server-side. The frontend only needs to send the selected `option_id`.

## NLU Behavior the Frontend Can Expose

For text turns, the response may include:

- `intent`
- `category`
- `confidence`
- `sentiment`
- `order_id`
- `entities`
- `source`

Useful frontend uses:

- debug panel
- analytics
- confidence-based observability

Do not use `nlu` as the source of navigation truth. The backend response already contains the resolved next state.

## Recommended Frontend Flow

1. Create a local session object.
2. Generate a `session_id`.
3. Initialize empty `context`.
4. Initialize empty `transcript`.
5. On each customer action, append the customer message to transcript.
6. Call `/chat/turn`.
7. Render `message`.
8. Render UI based on `render_type`.
9. Save `next_context` if present.
10. Append bot message to transcript.
11. End the session locally if `render_type` is `handover` or if your product treats terminal flows as closed.

## Minimal Frontend Example

```ts
type ChatContext = {
  current_flow?: string | null;
  flow_step?: string | null;
  category?: string | null;
  order_id?: string | null;
  turn_count: number;
  negative_turns: number;
  fallback_count: number;
  open_handovers: Array<{
    id: string;
    order_id?: string | null;
    issue_type?: string | null;
    status: string;
  }>;
};

type TranscriptMessage = {
  role: "customer" | "bot";
  content: string;
};

async function sendTurn(params: {
  sessionId: string;
  customerId?: string | null;
  message: string;
  messageType: "text" | "option_select" | "upload_complete";
  optionId?: string | null;
  context: ChatContext;
  transcript: TranscriptMessage[];
}) {
  const res = await fetch("/chat/turn", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      session_id: params.sessionId,
      customer_id: params.customerId ?? null,
      message: params.message,
      message_type: params.messageType,
      option_id: params.optionId ?? null,
      context: params.context,
      transcript: params.transcript
    })
  });

  if (!res.ok) {
    throw new Error(`chat/turn failed with ${res.status}`);
  }

  return res.json();
}
```

## Suggested UI Rules

- If `render_type === "options"`, show buttons and pause free typing until selection.
- If `render_type === "upload"`, show upload UI and advance only after upload completion.
- If `render_type === "text_input"`, keep composer enabled.
- If `render_type === "handover"`, lock the bot flow and show handover summary.
- If `options` is empty for an `options` response, allow normal text entry as a safe fallback.

## Notes and Implementation Quirks

- `message_type === "text"` is the only path that runs NLU in [app.py](/home/ashish/Documents/GitHub/Reatailgpt-mvp/app.py#L58).
- Option and upload turns rely entirely on `context.flow_step` and `option_id`.
- `current_flow` and `flow_step` are both set from the same next-step ID in [engine/flow_engine.py](/home/ashish/Documents/GitHub/Reatailgpt-mvp/engine/flow_engine.py#L22). Treat them as backend-owned state and pass them through unchanged.
- `terminal` exists in the response model, but current flow definitions mainly end through `flow_end` and rating flows rather than explicit terminal responses.
- `customer_id` is top-level in the request. It is not stored inside `context`.

## Best Practice Summary

- Keep state on the frontend.
- Always send the latest `context` and `transcript`.
- Use `next_context` exactly as returned.
- Drive UI from `render_type`.
- Treat `option_id` as the transition key for button clicks.
- Treat handover as session end for the automated assistant.
